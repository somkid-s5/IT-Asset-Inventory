# V1.1 Consistency, Data Integrity, and Realistic Acceptance

## Status

Proposed normative hardening specification derived from `docs/agents/SYSTEM_CONSISTENCY_AUDIT_2026-09-08.md`.

This specification does **not** expand the product into new business modules. It hardens the accepted V1 inventory so every existing module follows one data, lifecycle, UI, scale, and E2E contract.

## Problem Statement

V1 release acceptance proved that the accepted feature set can build, migrate, seed, run, and pass its defined browser suite. A deeper system audit found a second-order problem: several pages are individually functional but do not yet behave as one coherent product.

The same conceptual operation is expressed differently across Applications, Assets, VMs, Databases, vCenter Sources, Documents, Users, Audit Logs, Dashboard, and Data Quality. Some fields exist in DTO/schema but cannot be edited or inspected in the supported UI. Some lists and relation pickers silently operate on the first 100, 200, or 1000 records. Some API failures can render as empty or zero inventory. Some relationships are valid in the current dataset only because test data is clean, not because the write boundary prevents invalid cross-environment states.

The next release must therefore prioritize **truthfulness and consistency before further feature expansion**.

## Goal

Make the existing internal infrastructure inventory behave as one trustworthy operational system where:

- a user can understand every list/detail/action pattern after learning it once,
- every supported field has one clear source of truth and a complete round trip,
- API failures cannot look like valid empty data,
- relation pickers search the complete eligible inventory rather than a hidden prefix,
- cross-domain environment/lifecycle rules are server-enforced,
- Data Quality only asks for values the user can actually remediate,
- archive preserves history without leaving normal mutation ambiguous,
- Audit Logs describe lifecycle events accurately,
- realistic E2E proves persistence-backed workflows rather than only UI mocks,
- dense-data acceptance catches page-boundary failures before release.

## Product Principles

### 1. Truthful states

The UI MUST distinguish:

- initial loading,
- background refreshing,
- successful data,
- true empty dataset,
- filtered empty result,
- request failure with retry,
- forbidden access,
- not found.

A failed request MUST NOT render as zero counts, `No records found`, an empty relation picker, or an invented business state.

### 2. Round-trip parity

For every supported user-authored field:

`Create/Edit → API validation → DB persistence → API projection → Detail → future Edit`

MUST preserve the value.

Operationally important fields MUST also be observable in List, filters, Data Quality, Search, or Export as explicitly specified by the domain contract.

A field MUST NOT remain indefinitely in schema/DTO as a writable zombie field with no supported product workflow.

### 3. No invented business values

Read projections MUST preserve unknown as unknown.

Examples:

- null Database Status MUST NOT become `ACTIVE`,
- unknown Environment MUST NOT become PROD,
- request failure MUST NOT become count 0,
- archived/missing state MUST NOT be presented as active/synced.

### 4. Server-authoritative scale

Any user-visible search or relation picker that claims to search inventory MUST query the server over the complete eligible dataset.

Hard-coded silent caps such as 100, 200, or 1000 are prohibited unless the API also returns pagination metadata and the UI can reach all matching records.

### 5. Relationship integrity belongs to the backend

Frontend filtering is convenience, not integrity enforcement. Cross-domain relationship invariants MUST be rejected server-side.

### 6. Archive is preservation, not delete

Archive MUST preserve relationships, history, credentials, Documents, and identifiers unless an accepted domain rule explicitly says otherwise.

Archived records MUST remain readable. Normal mutation and new-link eligibility MUST follow one lifecycle policy.

### 7. One product presentation language

Status, Environment, Lifecycle, Data Quality, Query State, Row Actions, Table/Pagination, Date, and Missing Value rendering MUST use shared product-level patterns.

## User Stories

1. As an operator, I want request failures shown explicitly, so I never mistake an outage for an empty inventory.
2. As an operator, I want every list to use the same action and state grammar, so I do not relearn each module.
3. As an operator, I want Status, Environment, Lifecycle, Sync, and Data Quality visually distinct, so I do not confuse their meanings.
4. As an operator, I want values I enter to reappear predictably in Detail and future Edit, so I can trust persistence.
5. As an operator, I want Data Quality to link directly to an edit flow that contains the requested field.
6. As an operator, I want relation search to find a valid record even when it is item 201 or 1001.
7. As an operator, I want PROD topology to reject UAT/TEST compute or database links, so environment boundaries remain trustworthy.
8. As an operator, I want archived relationships visible as history but excluded from normal new-link choices.
9. As an operator, I want Application Access to belong unambiguously to one Environment.
10. As an operator, I want an explicit Primary Access rather than relying on database ordering.
11. As an operator, I want VM Owner, Business Unit, SLA Tier, Criticality, Service Role, and purpose to be editable and visible in Detail.
12. As an operator, I want VM lists to remain complete above 1000 records.
13. As an administrator, I want vCenter Source metadata edits to preserve credentials without forcing unnecessary credential re-entry.
14. As an administrator, I want Audit Logs to say Create, Update, Archive, Restore, Sync, Reveal, and Copy accurately.
15. As an administrator, I want Audit Log search and counts to cover the whole history, not only the first 100 rows.
16. As a maintainer, I want one dense acceptance dataset to expose hidden list/picker caps before release.

## Shared UI Contract

### InventoryTableShell

All inventory-style lists MUST use one shared structural contract providing:

- page title/description area,
- primary create/domain action,
- optional secondary module action,
- server-aware search/filter bar,
- active filter summary/reset,
- table or approved responsive representation,
- loading/error/empty/filtered-empty state handling,
- pagination metadata,
- standard row action placement.

The shell MAY allow domain-specific columns and toolbar actions, but MUST NOT allow each module to reinvent query-state behavior or pagination grammar.

### Row action contract

Default order:

1. row click/name link opens Detail,
2. Edit is an explicit standard action for writable active records,
3. domain-specific safe action may appear beside Edit where frequently used (for example vCenter Sync),
4. More menu contains secondary actions,
5. Archive/Restore is the lifecycle action at the bottom of the menu and requires the correct role/confirmation.

No row-selection checkbox is shown unless the page has a supported bulk action.

### Status family components

Create shared semantic renderers for at least:

- `RecordStatusBadge`
- `EnvironmentBadge`
- `VmLifecycleBadge`
- `VmPowerBadge`
- `VmSyncBadge`
- `QualityBadge`
- `SourceHealthBadge`

These components own labels/casing/tone. Pages MUST NOT maintain parallel local status maps for accepted values.

### Missing-value contract

Use semantic states:

- `Unknown` — value is not known,
- `Not applicable` — intentionally does not apply,
- `Needs context` — required by Data Quality and remediable,
- do not use `--` for business meaning except compact technical table cells where the shared formatter intentionally maps Unknown to a visual dash with accessible text.

### QueryState contract

All list and detail queries use a shared state decision layer:

- Loading
- Refreshing
- Error + Retry
- Forbidden
- Not Found
- Empty
- Filtered Empty
- Ready

HTTP 404, 403, and generic request errors MUST remain distinguishable.

## Shared Relation Picker Contract

Introduce one server-authoritative relation-search pattern reusable by Applications and Documents and available to future topology editors.

Minimum API/UI contract:

- resource kind,
- query string,
- page/cursor,
- bounded page size,
- `hasMore`/total metadata,
- safe display label + non-secret metadata,
- lifecycle eligibility,
- optional Environment filter,
- selected IDs remain visible even if outside the current search page,
- request error + retry,
- no hidden client-only global search over a partial list.

A normal picker MUST exclude archived records from new selections. Existing archived links remain visible in Detail/Edit as historical linked items and are labeled Archived.

## Application Contract

### Application Access

Application Access is owned by an Application Environment.

Every supported Access row MUST have:

- required `applicationId`,
- required `environmentId`,
- invariant `environment.applicationId === applicationId`,
- label,
- address,
- method,
- stable ordering,
- explicit `isPrimary` boolean.

At most one non-archived Primary Access exists per Environment. The list/detail UI MUST never infer Primary from array order.

Migration/backfill MUST validate existing rows before constraints are tightened. Existing valid rows must be preserved.

### Application Components

Component supports:

- name,
- description,
- stable ordering,
- Asset links,
- VM links,
- Logical Database links.

Description MUST be editable and visible in Detail.

Updating links MUST preserve existing relation metadata for retained relationships. A topology edit MUST NOT delete and recreate retained links in a way that silently loses `responsibleParty` or future metadata.

### Environment relationship rules

For a Component in Environment E:

- linked VM Environment MUST equal E,
- linked Logical Database parent Database Environment MUST equal E,
- archived VM/Database/Logical Database cannot be newly selected,
- existing archived links remain visible as historical context,
- Assets are not environment-authoritative in V1 and are therefore not rejected by Environment.

## Asset Contract

The supported Asset write model MUST decide each currently ambiguous field explicitly.

### Keep and expose

- Name
- Asset ID
- Type
- Brand/Model
- Serial Number
- Location
- Rack
- Parent
- Record Status
- Purchase Date
- Warranty Expiration
- Owner
- Department
- Responsible Party
- Vendor
- OS/Firmware Version when applicable
- Dependencies/operational dependency note if retained
- Application relationships
- Access Points + explicit credential relations
- hardware custom specifications

If `osVersion` and `dependencies` remain supported, they MUST have Edit controls and Detail presentation. Otherwise remove them from supported writable DTOs with a safe compatibility/migration plan.

### Remove/retire ambiguity

- Asset `environment` is not an authoritative V1 field and MUST be removed from normal writes after compatibility review.
- top-level `manageType` MUST not compete with per-Access-Point method. Access Point method is canonical for operational access.

### List contract

Owner/Location filters MUST expose active filter chips and the matching context must be inspectable through visible or optional columns.

Asset Type labels use one canonical map including `Service Processor` for stored value `SP`.

## VM Contract

### Curated context fields

VM Edit/Promotion MUST expose and persist:

- System Name / Service
- Environment
- Owner
- Business Unit
- SLA Tier
- Service Role
- Criticality
- Business Purpose / Description
- Operational Notes
- Tags
- Primary/Shared Application Components
- Guest Accounts

Data Quality MUST NOT require a field absent from this flow.

VM Detail MUST present Owner, Business Unit, SLA Tier, Criticality, Service Role, Environment, Purpose, Notes, and Application relationships in a predictable curation section.

### Source-owned facts

vCenter-owned facts remain read-only and are not changed by human curation.

### Lifecycle rules

- ACTIVE: normal edit permitted by role.
- DELETED_IN_VCENTER: curated context can be reviewed/updated only where operationally required; source facts remain source-owned.
- ARCHIVED: read-only normal Detail; Restore is Admin lifecycle action; no normal Edit.
- DRAFT/Discovery follows its accepted promotion workflow.

Copy MUST not suggest permanent delete where product UI does not support it.

### Scale

VM Discovery and Inventory list endpoints MUST support server-side search/filter/sort/pagination. No `take: 1000` completeness boundary is allowed.

The frontend MUST not download all VMs to implement the normal list.

## Database Contract

### Field parity

Database Form/Detail MUST reconcile:

- Name
- Engine
- Version
- Environment
- Host identity
- IP
- Port
- Service Name
- Owner
- Responsible Party if retained
- Backup Policy
- Replication
- Maintenance Window
- Status
- Note
- Logical Databases
- Accounts and scope
- Operational Client IP Metadata

Unknown Status stays unknown; UI MUST NOT substitute ACTIVE.

### Environment/host rule

If a Database is hosted by a VM, Database Environment MUST equal Host VM Environment.

If a Database changes Environment or Host VM, the resulting pair must still satisfy the invariant.

### Legacy metadata naming

The supported public contract should migrate away from misleading `linkedApps` naming toward `operationalClientIps` or another explicit neutral name. Compatibility may be retained temporarily at the service/DTO boundary, but UI and new API contracts MUST not imply canonical Application topology.

## vCenter Source Contract

### Credential-preserving edit

Source secrets are write-only.

Edit loads safe metadata and a `hasCredential`/equivalent indicator, never the secret.

If endpoint/username/password changes, a fresh Test Connection is required before Save.

If only Name/Sync Interval/Notes changes and existing credentials remain valid, Save MUST preserve credentials without forcing re-entry or a connection test.

Blank password on edit means preserve existing secret, not clear it.

### Audit taxonomy

Audit events MUST distinguish:

- CREATE_SOURCE
- UPDATE_SOURCE
- ARCHIVE_SOURCE
- RESTORE_SOURCE
- VCENTER_SYNC

If new enum values are required, add them through an explicit migration. Archive MUST not be logged as Delete when no deletion occurs.

## Documents Contract

Document authoring and public-boundary behavior remain as accepted in V1.

The inventory-link editor MUST use the Shared Relation Picker and therefore search the full eligible Applications/Assets/VMs/Databases dataset without 200/1000 hidden caps.

Failure to load relation options MUST show an error/retry state, not `No matching records`.

## Users Contract

User Management remains Admin-only.

- Remove row-selection UI unless a real bulk operation is introduced by a later spec.
- Role change, Password Reset, and Delete use a consistent privileged-action layout.
- Current-user safeguards remain enforced server-side.
- No new bulk user action enters V1.1.

## Audit Log Contract

Audit Logs MUST be server-authoritative for:

- pagination,
- search,
- action filtering,
- actor filtering where supported,
- date range where supported,
- sort,
- total count.

Summary values MUST be computed from the intended server dataset, not only the current frontend page.

The UI MUST be able to reach records beyond row 100.

Lifecycle taxonomy should be explicit enough that Archive/Restore can be filtered without parsing `details` strings.

## Dashboard and Data Quality Contract

Dashboard Overview request failure MUST render an explicit error state. Summary counts MUST never fall back to zero because data is unavailable.

Data Quality reasons retain stable machine-readable `code` values. Human labels/casing are normalized at presentation level.

For every context reason in Application, Asset, VM, and Database:

- Detail/Edit must contain a supported remediation control,
- Data Quality link must navigate to that record/workflow,
- saving a valid value must clear the backend reason,
- refetch must update the row without full application reload.

Route-mocked transition tests remain valid UI tests but are not release proof for persistence-backed remediation.

## Audit and Lifecycle Consistency

Across Applications, Assets, VMs, Databases, Logical Databases, and vCenter Sources:

- Create is logged as Create,
- normal change as Update,
- Archive as Archive,
- Restore as Restore,
- Reveal as Reveal/View Password,
- Copy as Copy Password,
- Sync as Sync.

Free-form details supplement the action; they do not substitute for the action taxonomy.

## Testing Strategy

### A. Contract/unit tests

Cover:

- field normalization,
- unknown-value preservation,
- Application Access ownership/primary invariant,
- retained relation metadata during topology updates,
- environment compatibility,
- archive eligibility,
- credential preservation,
- audit-action selection,
- query parameter validation.

### B. HTTP/integration tests

Prove backend authorization and data invariants through controllers/HTTP where practical, not only service mocks.

Required negative cases include:

- PROD Component + UAT VM → rejected,
- TEST Component + PROD Logical DB → rejected,
- PROD Database + UAT Host VM → rejected,
- archived record newly selected → rejected,
- duplicate Primary Access in one Environment → rejected.

### C. Persistence-backed browser journeys

Each major domain gets one realistic browser round trip against the isolated acceptance stack:

#### Application

Create → List → Detail → Edit ownership/description → Environment → Component description → link Asset/VM/Logical DB → add Primary Access + credential → reload → reveal/copy permission evidence → archive → restore → reload.

#### Asset

Create/edit all retained fields → Access Point/accounts → Primary/Shared Application relation → List filter → Detail parity → Data Quality remediation → archive/restore.

#### VM

Promote incomplete Discovery → Edit Owner/BU/SLA/Role/Criticality/Purpose → Data Quality clears → Detail parity → relation/credential preservation → archive read-only → restore.

#### Database

Create progressive record → host/environment validation → complete operations fields → Logical DB + account scope → Detail parity → Data Quality remediation → archive/restore.

#### vCenter Source

Create/test → metadata-only edit without secret re-entry → connection-affecting edit requires test → sync → archive → restore → audit actions.

#### Documents

Create/edit Document → server-search and link record beyond normal first page → reload → reverse navigation → public known-link regression.

#### Audit

Generate enough events to exceed first page → search an old event → navigate pages → filter lifecycle action → validate totals.

### D. Query-state browser matrix

Representative List and Detail surfaces MUST prove:

- 500/network error ≠ empty,
- 404 ≠ generic failure,
- retry succeeds without losing filter/query state,
- stale data may remain during background refresh without being labeled fresh if refresh fails.

### E. Dense-data boundary suite

Use an isolated generated fixture, separate from the small deterministic normal seed.

Minimum boundary values must cross known historical caps, for example:

- Assets: >200
- Databases: >200
- VM Inventory: >1000
- VM Discovery: >1000 where feasible
- Audit Logs: >100

Acceptance proves the last generated record can be searched, selected, linked, and paginated to where applicable.

### F. Persistence and release gates

After ticket integration:

- fresh migrations from zero,
- deterministic normal seed,
- dense fixture suite,
- backend build/tests,
- frontend lint/type/build,
- all new E2E journeys,
- existing V1 regression suite,
- HTTPS/secure-cookie checks,
- restart persistence,
- `git diff --check`.

## Migration Safety

- Do not destructively rewrite the user's main database during implementation.
- New constraints are first validated against isolated copies/acceptance DB.
- Backfills report ambiguous/invalid rows instead of silently guessing.
- Existing valid relationships and encrypted secrets are preserved.
- Compatibility fields are removed only after read/write consumers are traced and migration evidence is green.

## Implementation Order

1. Shared presentation/query contracts.
2. Shared relation picker/search contract.
3. Application integrity and E2E.
4. Asset parity cleanup.
5. VM curation + server-side scale.
6. Database parity/invariants.
7. vCenter Source credential/audit semantics.
8. Documents relation search.
9. Users/Audit/Dashboard consistency and scale.
10. Golden/dense data tooling.
11. Cross-domain realistic E2E.
12. Final integration/regression.

Foundation tickets MUST land before domain teams reproduce another local pattern.

## Out of Scope

- New Ticketing/ITSM modules
- Clients/CRM
- Notifications
- SLA workflow engine
- Automatic Application discovery
- Asset authoritative Environment modeling
- Permanent-delete UI
- Bulk user management
- New public Knowledge Base browsing
- Re-import of Sensitive Inventory Export
- A visual redesign unrelated to consistency contracts
- Replacing the existing framework/library stack solely for style reasons

## Definition of Done

V1.1 is done only when:

- every audit finding is mapped to a closed ticket or explicitly accepted exception,
- no supported Data Quality reason is impossible to remediate through UI,
- no supported relation picker has a silent completeness cap,
- no list/dashboard query failure can look like empty/zero data,
- all environment/lifecycle invariants are enforced server-side,
- shared status/query/action/table contracts are used by the accepted modules,
- realistic persistence-backed E2E passes,
- dense-data boundary acceptance passes,
- existing V1 release acceptance remains green,
- fresh migration/seed/HTTPS/restart-persistence gates remain green.
